This session has one phase: act as a **principal mobile product designer** and decide the best way to add a minimalistic "look up technique on YouTube" affordance to the app, then build it.

## The ask

While training, the user wants to tap an icon/button on the current exercise to open YouTube (app or website — whichever the mobile design pass decides is the right mechanism) with a search pre-filled from that exercise's real metadata, so they can quickly check proper technique. **Keep this minimalistic**: the goal is opening YouTube with the right search values, not building an embedded video browser, a curated video-link database, or anything that needs its own UI beyond one small tap target. No AI involved — this is a plain search-query handoff to an app the user already has.

## What this app actually is

Read `docs/product/next-task.md` and `docs/product/implementation-log.md` (newest entries first) before proposing anything — they're the source of truth and always current. Short version: a Spanish-first, iPhone-only web app (`https://gym.jcvalerio.com`) for building a workout plan manually and logging every set in the gym with RIR and pain. Single-column `max-w-md` layout, dark theme (zinc-950 background, emerald-300 accent), no design system beyond hand-written Tailwind classes, no icon library as a dependency (confirmed — `package.json` has none; every "icon" in the app today is a plain text/Unicode glyph: `−`, `+`, `←`, `▶`/`▼` from native `<details>`). Adding an icon library is a new dependency and needs explicit sign-off per this project's working conventions — don't add one unilaterally; a hand-written inline SVG or a plain text/Unicode glyph consistent with the rest of the app is the default expectation unless there's a real reason otherwise.

## What's verified, not assumed

- The most natural home for this is `session-runner.tsx` (`/entrenar/[sessionId]`), where "current exercise" is a well-defined concept (`currentExercise`) — the exercise name renders at `<h2 className="mt-2 text-xl font-semibold text-zinc-100">{currentExercise.exerciseNameEs}</h2>`, inside the same card that shows the prescription line, notes, and (since the last session) the "+ Agregar un set extra" bonus-set control and the "¿Por qué esta sugerencia?" link to `/guia`. Whether this also belongs on plan-preview/template-detail pages (`PlanDayPager`, `/plan/rutina`, `/plan/templates/[templateId]`) or the builder (`session-editor-form.tsx`) — anywhere else an exercise name is rendered before you're actually training it — is a real scope question for this session's design pass, not something to assume; the user's phrasing ("current exercise") points at the live session as the primary case.
- `exercisePrescription` fields available on every exercise: `exerciseNameEs` (always populated, Spanish-first), `exerciseNameEn` (nullable, currently unused everywhere else in the app per the standing "don't remove English support fields even though unused" constraint — worth a real decision on whether it's a useful fallback/addition for this feature specifically, not an automatic yes), `isUnilateral`, `loadMechanism`, `isCompound`, `notesEs`, `substitutionOptionsEs`. Spot-checked real template data: unilateral exercise names already tend to say so in Spanish (e.g. "Prensa unilateral," "Extensión de cuádriceps unilateral"), but not universally (e.g. "Sentadilla búlgara," "Zancada" are unilateral by nature without the word appearing) — decide deliberately whether the search query should append anything beyond the bare exercise name (a qualifier like "técnica" or "cómo hacer," and/or the unilateral flag when the name doesn't already say it), rather than guessing.
- The zero-dependency, "minimalistic" way to hand off to YouTube is a plain `<a href="https://www.youtube.com/results?search_query=...">` — no custom `youtube://` URL scheme, no fallback-detection JavaScript. iOS Safari already hands off `youtube.com` links to the installed YouTube app via universal links when present, and falls back to the mobile web results page in Safari when it isn't — this needs zero app-detection logic and matches "mostly opening the app or website with the right values" as literally as possible. **Verify this live on the real iPhone before considering it done** — universal-link handoff behavior can be finicky in practice (in-app-browser contexts, Safari settings, etc.) and the user already validated the rest of this app's mobile flow directly, so hold this feature to the same bar rather than trusting it from source alone.

## How to work

1. `nvm use v24.18.0`, then `npm run dev`. Use the Playwright MCP tools at an iPhone viewport (390×844) against the real dev DB, logged in as the real user (Google-OAuth-only; if you hit the sign-in screen, stop and ask the user to complete it). **Before touching `/entrenar`, check for a real in-progress workout session first** (a direct `psql` query against `workout_session` for `status = 'active'`, same as the last session did) — the account genuinely gets used for real training concurrently with development sessions on this project, so don't assume it's idle.
2. Present the placement/scope/mechanism decisions via `AskUserQuestion` for the genuine forks (at minimum: where the tap target lives and what it looks like given no icon library exists yet; whether scope extends beyond `/entrenar`; what exactly goes into the search query) — confirmed before implementing, matching how the last two features in this app were scoped.
3. Verify against real dev-DB data, including at least one unilateral exercise. Use the same throwaway-then-clean-up pattern already established in this project if any real session/set data needs to be touched for verification — delete afterward, confirmed via a direct query, never left behind.
4. Run before considering it done: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` (`nvm use v24.18.0` first). Add tests for whatever query-building logic gets extracted (a pure function mapping exercise metadata → search string is the natural unit-testable piece, matching this codebase's pattern of keeping URL/string-building logic in a plain `.ts` module rather than inline in the component).
5. Update `docs/product/implementation-log.md` (newest entry first) and `docs/product/next-task.md` after the change. Only commit when the user explicitly asks; only deploy when the user explicitly asks (and only once confirming no workout session is active, per the standing constraint).

## Constraints that still apply

- No AI plan generation — not relevant here, but keep in mind this app's whole "no AI generation" stance if the design pass is ever tempted to make this smarter than a search-query handoff.
- Spanish-first UX. `nameEn`/`notesEn` fields must not be removed even though unused elsewhere — a deliberate decision to use `exerciseNameEn` here (or not) is fine either way, just make it deliberately.
- Don't add a new dependency (an icon library, a deep-linking helper package, etc.) without flagging it explicitly and getting confirmation first.
- This is a real production app with a real active plan and real logged history — the same care about not touching real data applies here as it did for every prior feature.
