## The ask — five items, verbatim from real users

1. "I record during a training session for example the right weight but the wrong reps and I'm unable to update or correct the right values."
2. "I record the set information in the wrong exercise because I was moving between exercises and there is no way to edit."
3. "Some days I want to do a different exercise because the machine is broken/too busy or just because I don't feel well to perform that exercise, I would like to choose a different exercise from the plan or even create a new one."
4. "I'm 47 years old and the mobile app shows the text with small fonts even when my mobile settings are configured to show them in a bigger size, which made it harder to read instructions almost all the time."
5. "I want a better dashboard to see my progress — I have to tap the dropdown to change the exercise to see my progress. It would be nice to see all the exercises in a single chart or at least grouped by body part, muscle group, or whatever grouping makes more sense from the point of view of a physiotherapist or a personal trainer giving feedback — right now it's pretty basic."

Items 1 and 2 are really the same underlying gap (no way to correct a logged set) with two different triggers. Item 3 is a related but distinct gap (no way to change *what you're logging against*, before or during logging, not after). Item 4 is independent and small. Item 5 is the largest and most design-heavy — treat it as its own sub-session if it doesn't fit after 1–3.

## What this app actually is

Read `docs/product/next-task.md` and `docs/product/implementation-log.md` (newest entries first) before proposing anything — they're the source of truth and always current. Short version: a Spanish-first, iPhone-only web app (`https://gym.jcvalerio.com`) for building a workout plan manually and logging every set in the gym with RIR and pain. Single-column `max-w-md` layout, dark theme, no icon library as a dependency (every "icon" today is a plain text/Unicode glyph or a hand-written inline SVG — see the just-shipped YouTube-technique feature for the current inline-SVG precedent). No AI generation anywhere in the app — keep that framing intact even while making logging more flexible.

## What's verified, not assumed — grounded findings for each item

**Items 1 & 2 (correcting a logged set) — there is currently zero edit capability, confirmed at the repository layer.** `saveSetForSession` (`src/workouts/workout-repository.ts`) is insert-only: it derives `setNumber` from `existingSets.length + 1` and always does a plain `db.insert(setLog)`. There is no update or delete path anywhere in this codebase today — not a UI gap on top of a working backend, a completely missing capability end to end. `setLog` (`src/db/schema.ts`) has no `updatedAt` column, unlike `exerciseLog`/`workoutSession`, which both do — worth deciding whether an edit needs its own audit trail (when/whether a value was corrected) or a silent overwrite is fine for a personal training log.

The real judgment call: `suggestProgression` (`src/training/progression.ts`) and `splitPlannedAndBonusSets` (`src/workouts/progression-view.ts`) both read every logged set for an exercise instance directly — average RIR, top-of-range, rep-drop detection, and (since the bonus-set feature) planned-vs-bonus classification are all derived live from whatever is in `set_log`, not cached or snapshotted at completion time. That means editing a past set is *safe* in the sense that progression suggestions will simply reflect the corrected value going forward — there's no separate denormalized copy to keep in sync. But `splitPlannedAndBonusSets` classifies a set as planned-vs-bonus **by its position** among that exercise's sets (`setNumber` relative to `targetSets`), not by a stored flag — so item 2 (moving a set to a different exercise) isn't a simple "change the foreign key": it has to be re-inserted at the end of the target exercise's sequence (new `setNumber`), which could silently promote or demote its planned/bonus status, and could shift *other* sets in that exercise's own bonus/planned split too if the moved set displaces existing set numbers. Decide deliberately whether item 2 is "move this set to another exercise, keeping the same session" or the simpler, safer "delete the wrong entry, then re-log it correctly under the right exercise" — the second avoids the renumbering subtlety entirely and may be all users actually need, especially combined with a real fix for item 1.

**Item 3 (substitute/swap an exercise) — the schema already has a relevant field that goes almost entirely unused today.** `exercisePrescription.substitutionOptionsEs` (`jsonb`, `string[]`, max 3, already populated on several real templates — e.g. leg-priority's "Máquina equivalente, Cable equivalente") exists specifically for this scenario, but is currently rendered as inert static text in `session-runner.tsx`/`plan-page-content.tsx`, and **only when `painSensitive` is true** — not tappable, not exercise-specific data (just free-text labels a human wrote, not IDs pointing at real trackable exercises), and invisible for the large majority of exercises that aren't pain-flagged. Turning this into a real "log against this instead" flow raises a genuine architecture question worth a deliberate answer, not a default: does logging against a substitution create a real, permanent `exercisePrescription` row (so it accrues its own progression history over time, same as any other exercise), or is it a lighter, session-scoped override that doesn't touch the plan? The former is more useful long-term (a broken-machine substitution you use for a month should get real progression tracking) but is more schema/migration work; the latter is cheaper but means substituted sets don't build the kind of history the rest of this app is built around. The "or even create a new one" half of this ask is the bigger fork — a free-typed, unvetted exercise name mid-session has no `loadMechanism`/`isCompound`/`painSensitive` classification to drive progression suggestions or safety framing, unlike every other exercise in this app. Consider explicitly scoping the "create a new one" case down to *choosing from `substitutionOptionsEs`* (or from any other exercise already in the athlete's own plan) for this pass, and treating truly-arbitrary free-text exercise creation as a separate, later decision — flag this fork for `AskUserQuestion` rather than assuming the broader version is wanted.

**Item 4 (font size / accessibility) — root cause found, not just "fonts are small."** `src/app/layout.tsx`'s `viewport` export sets `maximumScale: 1`, which blocks pinch-to-zoom and Safari's own per-site "aA" text-size control on iOS — the two mechanisms mobile Safari actually offers for a user to make an under-sized web page's text bigger (unlike native apps, mobile Safari does not auto-apply the OS-level "Larger Text" accessibility setting to arbitrary web page CSS; it relies on the user zooming, which this line disables). This is a well-documented WCAG 1.4.4/1.4.10 violation pattern, not a subjective font-choice question. Tailwind's default `text-xs`/`text-sm`/etc. utilities are already `rem`-based (confirmed nothing in `globals.css` overrides a fixed root `font-size` in `px`), so removing `maximumScale: 1` (and confirming `userScalable` isn't separately forced off) is likely most of the real fix — verify live on a real iPhone with the accessibility Larger Text setting actually turned up, per this project's usual verification bar, rather than assuming the one-line fix is sufficient. Treat this as the smallest, lowest-risk, highest-confidence item — it doesn't need a design pass at all, only a real-device verification.

**Item 5 (dashboard) — the exact gap confirmed, and a direct conflict with a standing architectural decision already made in this project.** `/progreso`'s `exercise-progression-chart.tsx` renders exactly one exercise's chart at a time, switched via a `<select>` (`toExerciseSeriesGroups` in `src/workouts/exercise-series.ts` groups purely by exact `exerciseNameEs` string match) — matches the complaint precisely. But **this schema has no muscle-group or body-part field on any exercise, anywhere, by deliberate prior choice** — `exercisePrescription.loadMechanism`'s own doc comment in `schema.ts` explicitly warns it "replaces the old incrementCategory enum... which conflated equipment type with body region," and an earlier session (`docs/product/implementation-log.md`, 2026-08-02) explicitly declined to add per-exercise muscle-group classification for the same reason when it would have been useful for the unilateral-side-default feature. Grouping "by muscle group" as literally requested would reopen that exact decision — flag this plainly via `AskUserQuestion` rather than quietly adding a taxonomy field. Three real alternative grouping axes already exist in the data with zero new schema: **(a)** `planSessionTemplate.nameEs`/`.focus` — real template day names already read as body-region descriptions written by a human (e.g. "Femorales, glúteos y pantorrillas," "Tren superior completo A/B"), though this groups by the plan's *current* day structure, not a stable per-exercise property, so an exercise's group could change if the plan is edited; **(b)** `loadMechanism` × `isCompound` — a genuine trainer-relevant axis (compound machine work vs. isolation vs. bodyweight) that's already collected but currently unused for grouping anywhere; **(c)** `phase` (warmup/main/accessory/mobility). A single combined "all exercises in one chart" view (the other half of the request) is a separate, simpler ask from grouping — small multiples or a compact multi-line/sparkline layout per exercise, not necessarily one shared axis, since weight ranges vary wildly across exercises. Decide with the trainer/physio lens which axis (if any) a coach would actually reach for when reviewing someone's progress, then let the UX pass design the layout — don't let the engineering convenience of "no new schema" silently decide the coaching-relevant answer.

## How to work

1. `nvm use v24.18.0`, then `npm run dev`. Use the Playwright MCP tools at an iPhone viewport (390×844) against the real dev DB, logged in as the real user (Google-OAuth-only). **Before touching `/entrenar`, check for a real in-progress workout session first** — a direct `psql` query against `workout_session` for `status = 'active'`. **Use `grep '^DATABASE_URL=' .env.local`, not `grep DATABASE_URL .env.local | xargs`** — the latter also matches a second, commented-out fallback line further down the same file and silently exports the wrong one, a real mistake made and caught the hard way in the session that shipped the YouTube-technique feature (see that implementation-log entry for the full story). Verify you're pointed at the right branch before trusting any "no active session"/"no leftover rows" check.
2. Do the personal-trainer-with-physiotherapist-background pass first, before any UX work, on items 1–3 specifically: is unrestricted after-the-fact editing of a logged set safe for a training record meant to drive real progression suggestions, or does it need any guardrail (e.g., a visible "edited" marker, a time window, or just trusting the athlete — this is a personal single-user training log, not a coached multi-athlete platform, so lean toward trusting the athlete unless a concrete risk says otherwise)? For item 3, what's actually safe to substitute for what (a machine swap for the same movement pattern is low-risk; swapping a compound lower-body lift for an unrelated isolation exercise mid-plan is a real judgment call a physio would flag) — and is a caution note enough, or should some substitutions be discouraged.
3. Present the real forks via `AskUserQuestion`, confirmed before implementing (same pattern as every prior feature in this project): the edit mechanism/placement for items 1–2 (inline per-set edit vs. a dedicated edit view, and whether "wrong exercise" is a move or a delete-and-relog), the substitution mechanism and scope for item 3 (from `substitutionOptionsEs` only vs. any plan exercise vs. free-text creation — and whether a substitution becomes a real tracked `exercisePrescription` or a lighter override), and the grouping axis for item 5.
4. Given the real scope difference between these items, don't force all five into one sitting — item 4 is a same-session one-line fix; items 1–2 are one coherent unit; item 3 is its own unit; item 5 is likely its own session. Ship and verify incrementally, matching how every prior multi-piece session in this project (e.g. the competitor UX benchmark's 6 items) bundled only what was actually ready, not everything at once.
5. Verify against real dev-DB data, including at least one unilateral exercise where relevant. Use the same throwaway-then-clean-up pattern already established in this project for any real session/set data touched during verification — delete afterward, confirmed via a direct query, never left behind.
6. Run before considering any piece done: `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` (`nvm use v24.18.0` first). Add tests for any new pure logic (e.g. a set-edit validation function, a grouping function for the dashboard) matching this codebase's pattern of plain `.ts` modules with colocated tests.
7. Update `docs/product/implementation-log.md` (newest entry first) and `docs/product/next-task.md` after each shipped piece. Only commit when the user explicitly asks; only deploy when the user explicitly asks (and only once confirming no workout session is active).

## Constraints that still apply

- No AI plan generation or AI-assisted exercise creation — items 3's "create a new one" is a manual, user-typed addition if built at all, never an AI suggestion.
- Spanish-first UX. `exerciseNameEn`/`notesEn` fields must not be removed even though unused elsewhere.
- Preserve pain-aware framing: pain >2 blocks aggressive progression, pain >3 flags reduce/modify, pain >=7 flags stop/professional-guidance — an edited set's pain score should still drive this the same as any other.
- Don't add a new dependency (an icon library, a charting library for item 5, etc.) without flagging it explicitly and getting confirmation first — this app has shipped every chart so far as hand-rolled inline SVG.
- This is a real production app with a real active plan and real logged history — the same care about not touching real data applies here as it did for every prior feature.
